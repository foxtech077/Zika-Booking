# E6 — Booking Engine & Reservation Locks

*Last updated: 2026-04-25 | Status: Complete*

---

## 1. Epic Summary

E6 defines the full booking lifecycle: from the moment a guest taps "Book Now" through reservation lock acquisition, details entry, pricing confirmation, booking record creation, post-payment confirmation, cancellation handling, and automated completion. The core safety mechanism is a **5-minute atomic Redis reservation lock** that prevents two guests from simultaneously booking the same listing for the same dates. After the lock is acquired, the guest has 5 minutes to complete payment (E7); if the window lapses, the lock expires and the slot reopens. Booking records carry a human-readable reference in the format `KAIN-XXXX-CC`. The commission rate at the time of booking is snapshotted onto the record; the actual disbursement is handled in E11.

**Depends on:** E5 (Search & Discovery — Listing Detail page is the entry point), E7 (Payment System — payment initiation and outcome callbacks), E8 (Billing, Confirmation Email & PDF Voucher — triggered on booking confirmation).  
**Feeds into:** E7 (payment), E8 (confirmation email), E11 (commission calculation), E12 (Provider Dashboard booking list), E14 (Reviews — enabled after booking completion).

---

## 2. Actors

| Actor | Description |
|-------|-------------|
| **Guest (Authenticated)** | Logged-in user initiating and managing bookings. Authentication is mandatory to book. |
| **Provider** | Owner of the listed property or vehicle. May cancel confirmed bookings. Receives booking notifications. |
| **Booking Service** | Internal Node.js microservice. Owns booking records in PostgreSQL; orchestrates the lock, record creation, and status transitions. |
| **Redis** | Holds reservation locks (SETNX / Lua-scripted counters) with 5-minute TTL. |
| **Payment Service** | Internal microservice (E7). Processes payments and calls Booking Service back to confirm or fail a booking. |
| **Notification Service** | Internal microservice. Sends push and email notifications on booking events (E8 for emails). |
| **Scheduler** | Internal cron process. Runs nightly to transition `confirmed` bookings whose check-out / return date has passed to `completed`, and to clean up stale `pending_payment` records. |

---

## 3. Scope

**In scope (V1):**
- Reservation lock acquisition and expiry (Redis)
- Guest details entry (occupant / driver information)
- Pricing calculation snapshot (hotels, apartments, cars — including long-stay discount and car delivery fee)
- Booking record creation and reference generation (`KAIN-XXXX-CC`)
- Booking status state machine: `pending_payment → confirmed → completed` (happy path) plus cancellation states
- Guest-initiated cancellation with policy-based refund eligibility flag
- Provider-initiated cancellation
- System-initiated cancellation (lock timeout, payment failure)
- Automated booking completion (nightly job)
- Guest booking history and detail view

**Out of scope (other epics):**
- Payment processing and refund execution (E7)
- Confirmation email and PDF voucher generation (E8)
- Commission disbursement (E11)
- iCal blocking post-booking (E13)
- Reviews (enabled post-completion — E14)

## 4. Business Rules

| ID | Rule |
|----|------|
| **BR-6.1** | Booking requires an **authenticated Guest session** (valid JWT). Unauthenticated users are redirected to the login/registration screen; the intended listing and dates are preserved in deep-link state so the flow resumes after login. |
| **BR-6.2** | A guest may not book a listing they own as a provider. The Booking Service checks `listing.provider_id ≠ requesting_user.id` and rejects with HTTP 403 if they match. |
| **BR-6.3** | **Reservation lock — Hotels & Apartments:** On booking initiation the Booking Service executes `SET rlk:{listing_id}:{check_in}:{check_out} {lock_token} NX PX 300000` against Redis. NX means the command succeeds only if the key does not already exist. A successful SET indicates the slot is now held for 5 minutes. A failed SET (key exists) means another guest holds the lock; the initiating guest receives an "unavailable" response. |
| **BR-6.4** | **Reservation lock — Car Rentals (fleet):** Because `unit_count` may be > 1, a Lua script is used instead of SETNX. The app server first queries PostgreSQL for `confirmed_count` (bookings with `status IN ('confirmed', 'pending_payment')` overlapping the requested dates). The Lua script atomically reads the Redis counter `rlk:{listing_id}:{pickup_date}:{return_date}`, compares `counter + confirmed_count` against `unit_count`, and increments only if a slot remains. If the counter is already at capacity the initiation is rejected. Each slot increment carries a 300-second TTL reset on the counter key. |
| **BR-6.5** | The **lock token** is a UUID v4 generated by the Booking Service at initiation. It is returned to the client in the initiation response and must be included in all subsequent booking-flow API calls to verify the client holds the active lock. |
| **BR-6.6** | **Lock lifetime:** 300 seconds (5 minutes) from acquisition. The lock is released in three ways: (a) booking moves to `confirmed` — the Booking Service explicitly deletes the Redis key; (b) lock TTL expires naturally — Redis evicts the key; (c) guest explicitly abandons — client calls `DELETE /api/v1/bookings/lock/{lock_token}`, Booking Service deletes the key. |
| **BR-6.7** | **Lock expiry during flow:** If the lock TTL expires while the guest is still on the details or review screen, the next API call that validates the lock token receives HTTP 409 `lock_expired`. The client shows a full-screen modal: "Your reservation expired. The listing has been released." CTA: "Search again." No booking record is created in this scenario. |
| **BR-6.8** | **Booking reference format:** `KAIN-{SEQ}-{CC}` where `SEQ` is the next value from the PostgreSQL sequence `booking_seq` zero-padded to a minimum of 4 digits, and `CC` is the ISO 3166-1 alpha-2 country code of the listing. Examples: `KAIN-0001-KE`, `KAIN-0348-NG`, `KAIN-12004-ZA`. The reference is generated at the moment the `bookings` row is inserted (status `pending_payment`). |
| **BR-6.9** | **Pricing snapshot:** All pricing fields are captured on the `bookings` row at record creation and are immutable thereafter. Price changes on the listing after booking creation do not affect existing bookings. Fields snapshotted: `nightly_rate` / `daily_rate`, `currency`, `nights_or_days`, `subtotal`, `discount_amount`, `delivery_fee`, `total_amount`, `security_deposit`, `commission_rate`, `commission_amount`, `provider_payout`. |
| **BR-6.10** | **Commission rate snapshot:** The Booking Service reads the effective commission rate for the listing's country from the `commission_rates` table at booking creation time and stores it in `bookings.commission_rate`. The actual disbursement is handled in E11. |
| **BR-6.11** | **Pricing calculation — Hotels & Apartments:** `nights = check_out − check_in` (integer days). `subtotal = nightly_rate × nights`. If the apartment's `long_stay_discount_enabled = true` and `nights ≥ long_stay_min_nights`: if `discount_type = 'percentage'` then `discount_amount = subtotal × (discount_value / 100)`; if `discount_type = 'fixed'` then `discount_amount = discount_value × nights`. `total_amount = subtotal − discount_amount`. |
| **BR-6.12** | **Pricing calculation — Car Rentals:** `rental_days = CEIL((return_datetime − pickup_datetime) / 86400)` (partial days round up). `base_price = daily_rate × rental_days`. `delivery_fee = listing.delivery_fee` if `delivery_requested = true`, else 0. `total_amount = base_price + delivery_fee`. Security deposit is recorded in `bookings.security_deposit` but is **not charged at booking time** in V1; it is collected at vehicle pickup. |
| **BR-6.13** | **Booking status state machine:** Valid transitions are defined in §4 Status State Machine below. The Booking Service enforces that no invalid transition is persisted; any attempt is rejected with HTTP 409. |
| **BR-6.14** | **Cancellation policies** (set on listing, snapshotted on booking): `free` — full refund if cancelled ≥ 48 hours before check-in / pickup. `moderate` — full refund if cancelled ≥ 7 days before; 50% refund if cancelled 48 hours – 7 days before; no refund if < 48 hours. `strict` — 50% refund if cancelled ≥ 14 days before; no refund within 14 days. `non_refundable` — no refund regardless of timing. The Booking Service computes the applicable refund amount and sets `bookings.refund_amount`; the Payment Service (E7) executes the actual refund. |
| **BR-6.15** | **Provider cancellation:** A provider may cancel any `confirmed` booking at any time. Regardless of the listing's cancellation policy the guest always receives a **full refund** on a provider-initiated cancellation. The booking moves to `cancelled_by_provider`. The provider's cancellation count is incremented (tracked in E9 for moderation). |
| **BR-6.16** | **System cancellation:** If a `pending_payment` booking's payment is not confirmed within 10 minutes of record creation (a grace period beyond the 5-minute lock, allowing for slow payment processors), the Scheduler sets its status to `cancelled_by_system`. No payment has been captured at this point so no refund action is needed. The Redis lock will already have expired. |
| **BR-6.17** | **Completed bookings:** The Scheduler transitions `confirmed` bookings to `completed` the morning after the `check_out` date (hotels/apartments) or `return_datetime` (cars). A `completed` booking cannot be cancelled; any dispute is handled outside the platform's cancellation flow in V1. |
| **BR-6.18** | The `bookings` currency always matches `listing.currency`. No currency conversion is applied to the booking record; conversion for display purposes is informational only (BR-5.9). |
| **BR-6.19** | A guest may not have more than **5 `pending_payment` bookings** simultaneously across all listings. If the limit is reached, new booking initiations are rejected with HTTP 429 until existing pending bookings are confirmed, cancelled, or expire. |
| **BR-6.20** | After a booking reaches `confirmed`, the Booking Service publishes a `booking.confirmed` event. This event is consumed by: Notification Service (push + email to guest and provider), E8 (confirmation email + PDF voucher), E13 (iCal block creation). |

### 4.1 Booking Status State Machine

```
                        ┌──────────────────────────────────────────────────────────┐
                        │                    BOOKING STATUSES                       │
                        └──────────────────────────────────────────────────────────┘

  [Lock acquired]
        │
        ▼
 pending_payment ──── payment confirmed (E7 callback) ────► confirmed ──► completed
        │                                                        │
        │                                                        │
        ├── lock expires / payment timeout ──────────────► cancelled_by_system
        │
        └── (no record exists before this state)

 confirmed ──── guest cancels ───────────────────────────► cancelled_by_guest
 confirmed ──── provider cancels ────────────────────────► cancelled_by_provider
 confirmed ──── admin cancels (E9) ──────────────────────► cancelled_by_system
```

| From Status | To Status | Trigger | Actor |
|-------------|-----------|---------|-------|
| *(lock)* | `pending_payment` | Guest submits booking details + payment initiated | Booking Service |
| `pending_payment` | `confirmed` | Payment Service callback: payment successful | Payment Service |
| `pending_payment` | `cancelled_by_system` | Payment timeout (10 min) or payment failure | Scheduler / Payment Service |
| `confirmed` | `completed` | Check-out / return date passed (nightly job) | Scheduler |
| `confirmed` | `cancelled_by_guest` | Guest requests cancellation | Guest |
| `confirmed` | `cancelled_by_provider` | Provider requests cancellation | Provider |
| `confirmed` | `cancelled_by_system` | Admin overrides (E9) | Admin |

## 5. Use Cases

### UC-6.1 — Initiate Booking & Acquire Reservation Lock

**Primary Actor:** Guest (Authenticated)  
**Preconditions:**
- Guest is on a Listing Detail page (UC-5.8 or UC-5.9) with valid dates/datetimes selected.
- The listing has `status = 'approved'` (hotel) or `status = 'active'` (apartment, car).
- Guest is authenticated (valid JWT).

**Postconditions:**
- A reservation lock is held in Redis for 5 minutes.
- Guest advances to the Details Entry screen (UC-6.2).
- If lock acquisition fails, guest sees an "unavailable" message and is not advanced.

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | Guest | Taps **Book Now** on the Listing Detail page. Client sends `POST /api/v1/bookings/initiate` with `{ listing_id, check_in, check_out, guests }` (hotels/apartments) or `{ listing_id, pickup_datetime, return_datetime, delivery_requested }` (cars). JWT in Authorization header. |
| 2 | System | Booking Service validates: guest is authenticated; listing exists and is active/approved; guest does not own the listing (BR-6.2); date/time parameters pass BR-5.4 rules; guest is not at the pending-booking limit (BR-6.19). |
| 3 | System | **Hotels/Apartments:** Executes `SET rlk:{listing_id}:{check_in}:{check_out} {lock_token} NX PX 300000` against Redis. |
|   |        | **Cars:** Queries PG for `confirmed_count` of overlapping bookings. Executes Lua script to atomically compare and increment the Redis fleet counter. |
| 4 | System | Lock acquired. Generates `lock_token` (UUID v4). Stores `{ listing_id, guest_id, check_in, check_out, lock_token, expires_at }` in Redis alongside the lock key for context retrieval. |
| 5 | System | Returns HTTP 200: `{ lock_token, expires_at, booking_context: { listing_id, listing_type, nightly_rate / daily_rate, currency, nights / rental_days, pricing_preview } }`. |
| 6 | System | Client starts a **countdown timer** displayed in the booking flow UI (e.g., "Complete your booking in 4:57"). |
| 7 | Guest | Advances to the Guest Details Entry screen (UC-6.2). |

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.1A | Guest is not authenticated | Client detects missing JWT. Redirects to login screen. On successful login, deep-link state restores `listing_id` and dates. Guest is returned to the Listing Detail page and must tap Book Now again. |
| AF-6.1B | Guest already holds an active lock on this listing+dates | Redis key exists with the same guest's `lock_token`. Booking Service returns the existing `lock_token` and remaining TTL instead of creating a new lock. Guest resumes the in-progress flow. |

**Exception Flows:**

| ID | Trigger | System Response |
|----|---------|-----------------|
| EX-6.1A | Redis lock key exists (another guest holds it) | HTTP 409 `listing_unavailable`. Client shows modal: "This listing is being reserved by another guest. Please try again in a few minutes." No lock is acquired. |
| EX-6.1B | Listing status changed to inactive between detail page load and Book Now tap | Booking Service re-checks listing status. HTTP 410. Client shows: "This listing is no longer available." with Search Again CTA. |
| EX-6.1C | Guest is at the 5 pending-booking limit (BR-6.19) | HTTP 429. Client shows: "You have too many pending reservations. Please complete or cancel an existing booking before starting a new one." |
| EX-6.1D | Redis is unreachable | Booking Service returns HTTP 503. Client shows: "Booking is temporarily unavailable. Please try again." No booking record is created. |

**Data Entities Touched:** Redis (SET lock key), `listings` (read status check)  
**API Endpoints:** `POST /api/v1/bookings/initiate`

### UC-6.2 — Enter Guest & Booking Details

**Primary Actor:** Guest (Authenticated)  
**Preconditions:**
- Reservation lock is active (`lock_token` is valid and not expired).
- Guest is on the Details Entry screen.

**Postconditions:**
- All required guest and occupant/driver details have been captured in client state.
- Guest advances to the Review & Pricing screen (UC-6.3).
- Countdown timer continues ticking.

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | System | Details Entry screen pre-fills with the guest's account data: `first_name`, `last_name`, `email`, `phone`. Guest may edit these for the booking (edits do not change the account profile). |
| 2 | Guest | Reviews/edits primary guest details: First name *, Last name *, Email *, Phone number (optional). |
| 3 | Guest | **(Hotels/Apartments only)** Enters: Number of adults (≥ 1), Number of children (≥ 0). For apartments, the system validates `adults + children ≤ listing.max_guests` (inline error if exceeded). |
| 4 | Guest | **(Hotels/Apartments only)** Enters special requests (optional free-text, max 500 chars). |
| 5 | Guest | **(Car Rentals only)** Enters driver details: Driver first name *, Driver last name *, Driver age *. System validates `driver_age ≥ listing.min_driver_age` (inline error if underage). |
| 6 | Guest | **(Car Rentals — if delivery requested)** Enters delivery address (street, city, country). Validation: address is within `delivery_radius_km` of the listing's pickup location. |
| 7 | Guest | Taps **Continue**. Client validates all required fields are present. |
| 8 | System | Client stores details in local booking state (no API call at this step — details are submitted in UC-6.3). |
| 9 | Guest | Advances to the Review & Pricing screen (UC-6.3). |

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.2A | Guest changes number of guests beyond `max_guests` (apartments) | Inline validation error: "This apartment accommodates a maximum of [N] guests." Continue button remains disabled. |
| AF-6.2B | Driver age < listing `min_driver_age` (cars) | Inline error: "The minimum driver age for this vehicle is [N] years." Continue is disabled. |
| AF-6.2C | Delivery address is outside `delivery_radius_km` | After the address is entered, client calls `GET /api/v1/listings/:id/delivery-check?address=...`. System returns `{ in_range: false, max_km: N }`. Inline error: "Delivery is only available within [N] km of the pickup location." |
| AF-6.2D | Countdown timer reaches 0:30 (30 seconds remaining) | A yellow warning banner appears: "Your reservation expires in 30 seconds!" with a **Renew (30s)** button. Tapping it calls `POST /api/v1/bookings/lock/renew` with the `lock_token`. System attempts to extend the lock by resetting its TTL to 300s (only allowed once per lock lifetime). |

**Exception Flows:**

| ID | Trigger | System Response |
|----|---------|-----------------|
| EX-6.2A | Guest taps Continue but lock has already expired | Client's countdown reaches 0. Lock expiry modal is displayed (see BR-6.7). Guest cannot proceed. |

**Data Entities Touched:** None (client-side state only at this step)  
**API Endpoints:** `GET /api/v1/listings/:id/delivery-check` (optional, AF-6.2C), `POST /api/v1/bookings/lock/renew` (optional, AF-6.2D)

### UC-6.3 — Review Booking Summary & Pricing

**Primary Actor:** Guest (Authenticated)  
**Preconditions:**
- Reservation lock is active.
- Guest has completed the Details Entry screen (UC-6.2).

**Postconditions:**
- Guest has reviewed a complete pricing breakdown and all booking details.
- Guest taps **Proceed to Payment**, which hands off to E7 (Payment Service).
- A `pending_payment` booking record is created in PostgreSQL with a generated reference.

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | System | Review screen displays a read-only summary of all booking details collected in UC-6.1 and UC-6.2. Guest may tap **Edit** to return to the Details screen. |
| 2 | System | Displays the **Pricing Breakdown** panel (see tables below). |
| 3 | System | Displays the **Cancellation Policy** summary for the listing. |
| 4 | System | Displays the **Terms** checkbox: "I agree to ZikaBooking's Terms of Service and the above cancellation policy." Unchecked by default. |
| 5 | Guest | Reads the summary. Checks the Terms checkbox. |
| 6 | Guest | Taps **Proceed to Payment**. |
| 7 | System | Client sends `POST /api/v1/bookings` with the full booking payload: `{ lock_token, listing_id, check_in, check_out, guests, special_requests, guest_details, driver_details (cars), delivery_requested, delivery_address (cars) }`. |
| 8 | System | Booking Service validates the `lock_token` is still active in Redis and belongs to this guest. |
| 9 | System | Booking Service re-computes the full pricing snapshot server-side (never trust client-side totals). Fetches the current commission rate for the listing's country. |
| 10 | System | Inserts a new row into `bookings` with `status = 'pending_payment'`. Generates the booking reference `KAIN-{nextval('booking_seq')}-{country_code}`. |
| 11 | System | Returns HTTP 201: `{ booking_id, booking_reference, total_amount, currency, payment_context }`. The `payment_context` is consumed by the Payment Service (E7) to initiate the payment session. |
| 12 | System | Client hands off to the Payment flow (E7 — UC-7.1). |

**Pricing Breakdown — Hotels & Apartments:**

| Line Item | Calculation | Displayed As |
|-----------|-------------|--------------|
| Room / apartment rate | `nightly_rate × nights` | KES 8,500 × 3 nights = KES 25,500 |
| Long-stay discount | `−(subtotal × discount_pct)` or `−(discount_value × nights)` | − KES 2,550 (10% discount) |
| **Total** | `subtotal − discount_amount` | **KES 22,950** |

**Pricing Breakdown — Car Rentals:**

| Line Item | Calculation | Displayed As |
|-----------|-------------|--------------|
| Rental rate | `daily_rate × rental_days` | KES 4,500 × 5 days = KES 22,500 |
| Delivery fee | `delivery_fee` (if requested) | + KES 500 |
| **Total** | `base_price + delivery_fee` | **KES 23,000** |
| Security deposit | `security_deposit` (held at pickup, not charged now) | KES 10,000 *(collected at pickup)* |

*Note: Platform commission is not shown to guests. It is deducted from the provider's payout (E11).*

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.3A | Server-computed price differs from the client's preview price (e.g., listing price changed between lock acquisition and review submission) | Because the lock was acquired against the listing's current state and prices are immutable once locked, this cannot happen in normal operation. If it occurs (e.g., a race with a price edit), the server returns the authoritative price in the response. The client re-renders the review screen with a notice: "The price has been updated. Please review the new total." Guest must re-tap Proceed to Payment. |
| AF-6.3B | Guest taps **Edit** | Returns to UC-6.2. Lock timer continues. |

**Exception Flows:**

| ID | Trigger | System Response |
|----|---------|-----------------|
| EX-6.3A | `lock_token` is invalid or expired when `POST /api/v1/bookings` is submitted | HTTP 409 `lock_expired`. Lock expiry modal displayed (BR-6.7). No booking record created. |
| EX-6.3B | Listing status changed to inactive between lock acquisition and booking creation | Booking Service re-validates listing status at insert time. HTTP 410. Lock is released. Client shows: "This listing is no longer available." |

**Data Entities Touched:** `bookings` (INSERT — `pending_payment`), `commission_rates` (read), `listings` (read for price + policy snapshot)  
**API Endpoints:** `POST /api/v1/bookings`

### UC-6.4 — Reservation Lock Expiry Handling

**Primary Actor:** System (Redis TTL eviction), Guest  
**Preconditions:**
- A reservation lock exists in Redis.
- The 5-minute TTL has elapsed before the booking was confirmed.

**Postconditions:**
- The Redis lock key no longer exists (evicted by TTL).
- If a `pending_payment` booking record exists, it is eventually set to `cancelled_by_system` by the Scheduler (BR-6.16).
- Guest is shown a contextual "expired" message.

**Main Success Scenario — Lock Expires During Details Entry or Review:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | System | Client-side countdown timer reaches 0:00. |
| 2 | System | Client displays full-screen expiry modal: "Your reservation has expired. The listing has been released for other guests." Single CTA: **Search Again**. All booking flow screens are inaccessible. |
| 3 | Guest | Taps **Search Again**. Client navigates back to the Search Results page (UC-5.2 / UC-5.3) with the same search parameters. |

**Main Success Scenario — Lock Expires During Payment (no booking record yet):**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | System | Payment Service calls `POST /api/v1/bookings` (UC-6.3 step 7) but the lock has expired in Redis. |
| 2 | System | Booking Service returns HTTP 409 `lock_expired`. No `bookings` row is created. |
| 3 | System | Payment flow is aborted before any charge is captured. Client shows expiry modal (step 2 above). |

**Main Success Scenario — Stale `pending_payment` Record Cleanup (Scheduler):**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | Scheduler | Nightly job runs: `SELECT id FROM bookings WHERE status = 'pending_payment' AND created_at < NOW() − INTERVAL '10 minutes'`. |
| 2 | Scheduler | For each stale record: updates `status = 'cancelled_by_system'`, inserts into `booking_status_log`. No refund action (no payment was captured). |
| 3 | System | `booking.cancelled_by_system` event published. (No guest notification for system auto-cancellations in V1.) |

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.4A | Guest taps **Renew** (AF-6.2D) before expiry | `POST /api/v1/bookings/lock/renew` with `lock_token`. Booking Service verifies the lock still exists (key in Redis) and that it has not already been renewed. Resets TTL to 300s. Returns updated `expires_at`. Client countdown resets. Renewal is allowed **once per lock lifetime**. |
| AF-6.4B | Guest attempts renewal but lock is already expired | HTTP 409 `lock_expired`. Client shows expiry modal. |

**Exception Flows:** None — expiry is a deterministic TTL event; no error handling is required beyond the guest-facing modal.

**Data Entities Touched:** Redis (key evicted by TTL), `bookings` (status UPDATE to `cancelled_by_system` for stale records), `booking_status_log` (INSERT)  
**API Endpoints:** `POST /api/v1/bookings/lock/renew`, `DELETE /api/v1/bookings/lock/{lock_token}` (explicit abandon)

### UC-6.5 — Confirm Booking (Post-Payment Callback)

**Primary Actor:** Payment Service (E7)  
**Preconditions:**
- A `pending_payment` booking record exists.
- Payment Service has successfully charged the guest (E7 — UC-7.x).

**Postconditions:**
- `bookings.status = 'confirmed'`, `confirmed_at = NOW()`.
- Redis lock is released.
- `booking.confirmed` event published (triggers E8 confirmation email + PDF voucher, E13 iCal block, push notifications).

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | Payment Service | Calls `PATCH /api/v1/bookings/{booking_id}/confirm` with `{ payment_id, payment_provider }` (internal service-to-service call; mTLS authenticated). |
| 2 | Booking Service | Validates: `booking.status = 'pending_payment'`; booking record exists. |
| 3 | Booking Service | Atomically updates: `status = 'confirmed'`, `confirmed_at = NOW()`, `payment_id = {payment_id}`. Inserts row in `booking_status_log`. |
| 4 | Booking Service | Deletes Redis lock key `rlk:{listing_id}:{dates}` (BR-6.6(a)). For cars, decrements the fleet counter and removes the slot. |
| 5 | Booking Service | Publishes `booking.confirmed` event with full booking payload. |
| 6 | Notification Service | Sends push notification to guest: "Booking confirmed! 🎉 Your booking at [Listing Title] (Ref: KAIN-XXXX-CC) is confirmed." |
| 7 | Notification Service | Sends push notification to provider: "New booking! [Guest Name] booked [Listing Title] — [check_in] to [check_out]." |
| 8 | E8 | Generates and sends confirmation email with PDF voucher to guest. |
| 9 | E13 | Creates iCal block for the booked date range. |
| 10 | System | Client (polling or WebSocket) receives the confirmation. Navigates to the Booking Confirmation screen showing: reference number, listing title and photo, dates, total paid, and a "View Booking" CTA. |

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.5A | `booking.status ≠ 'pending_payment'` when confirm callback arrives (duplicate call) | Booking Service returns HTTP 409. If status is already `confirmed`, the duplicate is idempotent and does not re-publish the event. If status is `cancelled_by_system`, returns HTTP 410 — booking was already cleaned up; Payment Service must initiate a full refund. |

**Exception Flows:**

| ID | Trigger | System Response |
|----|---------|-----------------|
| EX-6.5A | Redis lock deletion fails (Redis unreachable) | Booking is still confirmed in PostgreSQL. Redis lock will expire naturally within its remaining TTL. Log a warning. The listing will briefly appear "locked" to other guests but will free up within minutes. |
| EX-6.5B | `booking.confirmed` event publish fails | Booking is confirmed in PG. Retry queue (at-least-once delivery) will re-publish the event. Duplicate-safe consumers in E8/E13/Notification Service handle potential re-delivery via idempotency keys. |

**Data Entities Touched:** `bookings` (UPDATE confirmed), `booking_status_log` (INSERT), Redis (DEL lock key)  
**API Endpoints:** `PATCH /api/v1/bookings/{booking_id}/confirm` (internal)

### UC-6.6 — Payment Failure Handling

**Primary Actor:** Payment Service (E7)  
**Preconditions:**
- A `pending_payment` booking record exists.
- Payment processing has failed (card declined, insufficient funds, Tara API error, etc.).

**Postconditions:**
- `bookings.status = 'cancelled_by_system'`.
- Redis lock is released.
- Guest is returned to the payment screen with an error message and the option to retry with a different payment method (within a new lock window) or abandon.

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | Payment Service | Calls `PATCH /api/v1/bookings/{booking_id}/fail` with `{ failure_reason }` (internal). |
| 2 | Booking Service | Updates `status = 'cancelled_by_system'`, logs reason. Deletes Redis lock key. |
| 3 | Payment Service | Returns the failure reason to the client. |
| 4 | System | Client shows payment error screen: "[Failure reason, e.g., 'Card declined']. Your reservation has been released. Would you like to try again?" CTAs: **Try Again** (re-initiates a new lock — UC-6.1) or **Cancel**. |

**Data Entities Touched:** `bookings` (UPDATE cancelled_by_system), `booking_status_log` (INSERT), Redis (DEL)  
**API Endpoints:** `PATCH /api/v1/bookings/{booking_id}/fail` (internal)

### UC-6.7 — Guest-Initiated Cancellation

**Primary Actor:** Guest (Authenticated)  
**Preconditions:**
- Booking has `status = 'confirmed'`.
- Guest is authenticated and owns the booking (`booking.guest_id = requesting_user.id`).

**Postconditions:**
- `bookings.status = 'cancelled_by_guest'`, `cancelled_at = NOW()`.
- Refund amount computed per cancellation policy and stored in `bookings.refund_amount`.
- Payment Service instructed to process the refund (E7).
- Notification sent to provider.

**Main Success Scenario:**

| Step | Actor | Action / System Response |
|------|-------|--------------------------|
| 1 | Guest | Navigates to **My Bookings** → taps the booking → taps **Cancel Booking**. |
| 2 | System | Displays a cancellation preview modal: policy name, refund amount ("You will receive [amount] back to your original payment method"), and the effective date. |
| 3 | Guest | Taps **Confirm Cancellation**. |
| 4 | System | Client sends `POST /api/v1/bookings/{booking_id}/cancel` with `{ reason (optional free-text) }`. JWT required. |
| 5 | Booking Service | Validates: `booking.status = 'confirmed'`; `booking.guest_id = requesting_user.id`; booking is not `completed`. |
| 6 | Booking Service | Computes `refund_amount` based on `bookings.cancellation_policy` and the time elapsed since booking vs. check-in date (BR-6.14). |
| 7 | Booking Service | Updates `status = 'cancelled_by_guest'`, `cancelled_at = NOW()`, `cancelled_by = 'guest'`, `cancellation_reason`, `refund_amount`. Inserts `booking_status_log`. |
| 8 | Booking Service | Calls Payment Service to initiate refund of `refund_amount` (E7 — UC-7.x). |
| 9 | Booking Service | Publishes `booking.cancelled_by_guest` event. |
| 10 | Notification Service | Sends push + email to provider: "[Guest Name] cancelled their booking (Ref: KAIN-XXXX-CC) for [dates]." |
| 11 | E13 | Removes the iCal block for the cancelled date range. |
| 12 | System | Client shows: "Booking cancelled. [Refund amount] will be returned to your [payment method] within 5–10 business days." |

**Cancellation Policy Refund Computation:**

| Policy | Cancellation Timing | Refund Amount |
|--------|---------------------|---------------|
| `free` | ≥ 48 h before check-in / pickup | 100% of `total_amount` |
| `free` | < 48 h before check-in / pickup | 0% |
| `moderate` | ≥ 7 days before | 100% |
| `moderate` | 48 h – 7 days before | 50% |
| `moderate` | < 48 h | 0% |
| `strict` | ≥ 14 days before | 50% |
| `strict` | < 14 days | 0% |
| `non_refundable` | Any time | 0% |

**Alternative Flows:**

| ID | Trigger | Steps |
|----|---------|-------|
| AF-6.7A | Cancellation policy computes 0% refund | Modal shows: "No refund is available under the [Policy] cancellation policy. Are you sure you want to cancel?" Guest must confirm explicitly. |
| AF-6.7B | Booking is in `pending_payment` state (rare race) | Client shows: "Your payment is being processed and cannot be cancelled at this time. Please wait for confirmation, then cancel if needed." |

**Exception Flows:**

| ID | Trigger | System Response |
|----|---------|-----------------|
| EX-6.7A | `booking.status = 'completed'` | HTTP 409. Client shows: "Completed bookings cannot be cancelled. Please contact support for disputes." |
| EX-6.7B | Guest attempts to cancel another guest's booking | HTTP 403. |

**Data Entities Touched:** `bookings` (UPDATE cancelled_by_guest), `booking_status_log` (INSERT)  
**API Endpoints:** `POST /api/v1/bookings/{booking_id}/cancel`

## 6. Data Model

```sql
-- PostgreSQL sequence for booking reference generation
CREATE SEQUENCE booking_seq START 1 INCREMENT 1 NO CYCLE;

CREATE TABLE bookings (
    id                      UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    reference               VARCHAR(25)     UNIQUE NOT NULL,
    -- KAIN-{SEQ}-{CC}, e.g. KAIN-0001-KE

    listing_id              UUID            NOT NULL REFERENCES listings(id),
    guest_id                UUID            NOT NULL REFERENCES users(id),
    provider_id             UUID            NOT NULL,
    -- denormalized from listing at creation time; provider_users table (E12)
    listing_type            VARCHAR(20)     NOT NULL CHECK (listing_type IN ('hotel', 'apartment', 'car')),

    -- Status
    status                  VARCHAR(30)     NOT NULL DEFAULT 'pending_payment'
                                            CHECK (status IN (
                                                'pending_payment',
                                                'confirmed',
                                                'completed',
                                                'cancelled_by_guest',
                                                'cancelled_by_provider',
                                                'cancelled_by_system'
                                            )),

    -- Stay / rental period
    check_in                DATE,           -- hotels, apartments
    check_out               DATE,           -- hotels, apartments
    pickup_datetime         TIMESTAMPTZ,    -- cars
    return_datetime         TIMESTAMPTZ,    -- cars
    nights_or_days          SMALLINT        NOT NULL,

    -- Guest details (snapshot at booking time)
    guest_first_name        VARCHAR(100)    NOT NULL,
    guest_last_name         VARCHAR(100)    NOT NULL,
    guest_email             VARCHAR(255)    NOT NULL,
    guest_phone             VARCHAR(30),
    adults                  SMALLINT,
    children                SMALLINT        DEFAULT 0,
    special_requests        TEXT,

    -- Driver / car-specific
    driver_first_name       VARCHAR(100),
    driver_last_name        VARCHAR(100),
    driver_age              SMALLINT,
    delivery_requested      BOOLEAN         DEFAULT FALSE,
    delivery_address        TEXT,

    -- Pricing snapshot (immutable after creation — BR-6.9)
    nightly_rate            NUMERIC(12, 2),
    daily_rate              NUMERIC(12, 2),
    subtotal                NUMERIC(12, 2)  NOT NULL,
    discount_amount         NUMERIC(12, 2)  NOT NULL DEFAULT 0,
    delivery_fee            NUMERIC(12, 2)  NOT NULL DEFAULT 0,
    total_amount            NUMERIC(12, 2)  NOT NULL,
    currency                CHAR(3)         NOT NULL,
    security_deposit        NUMERIC(12, 2),

    -- Commission snapshot (immutable — BR-6.10)
    commission_rate         NUMERIC(6, 4)   NOT NULL,
    commission_amount       NUMERIC(12, 2)  NOT NULL,
    provider_payout         NUMERIC(12, 2)  NOT NULL,

    -- Cancellation policy snapshot
    cancellation_policy     VARCHAR(20)     NOT NULL
                                            CHECK (cancellation_policy IN ('free', 'moderate', 'strict', 'non_refundable')),
    refund_amount           NUMERIC(12, 2),

    -- Cancellation fields
    cancelled_at            TIMESTAMPTZ,
    cancelled_by            VARCHAR(20)     CHECK (cancelled_by IN ('guest', 'provider', 'system')),
    cancellation_reason     TEXT,

    -- Payment linkage (set on confirmation)
    payment_id              UUID,           -- FK to payments table (E7)

    -- Timestamps
    confirmed_at            TIMESTAMPTZ,
    completed_at            TIMESTAMPTZ,
    created_at              TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at              TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_bookings_guest       ON bookings(guest_id, created_at DESC);
CREATE INDEX idx_bookings_listing     ON bookings(listing_id, status);
CREATE INDEX idx_bookings_provider    ON bookings(provider_id, created_at DESC);
CREATE INDEX idx_bookings_status      ON bookings(status, created_at DESC);
CREATE INDEX idx_bookings_check_in    ON bookings(check_in) WHERE status IN ('confirmed');
CREATE INDEX idx_bookings_checkout    ON bookings(check_out) WHERE status = 'confirmed';
CREATE INDEX idx_bookings_return      ON bookings(return_datetime) WHERE status = 'confirmed';
CREATE UNIQUE INDEX idx_bookings_ref  ON bookings(reference);

-- Audit trail of every status transition
CREATE TABLE booking_status_log (
    id          UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    booking_id  UUID            NOT NULL REFERENCES bookings(id) ON DELETE CASCADE,
    from_status VARCHAR(30),
    to_status   VARCHAR(30)     NOT NULL,
    changed_by  UUID,           -- user_id (guest or provider) or NULL for system/scheduler
    actor_type  VARCHAR(20)     CHECK (actor_type IN ('guest', 'provider', 'admin', 'system')),
    reason      TEXT,
    created_at  TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_status_log_booking ON booking_status_log(booking_id, created_at DESC);
```

## 8. Acceptance Criteria

### AC-6.1 — Reservation Lock
- [ ] Two simultaneous `POST /api/v1/bookings/initiate` requests for the same hotel listing and overlapping date range result in exactly one success (HTTP 200) and one failure (HTTP 409 `listing_unavailable`).
- [ ] A car listing with `unit_count = 3` and 2 confirmed bookings for a date range allows exactly 1 more concurrent lock to be acquired; a 5th simultaneous initiation is rejected.
- [ ] A reservation lock key is absent from Redis 300 seconds after acquisition with no renewal.
- [ ] A lock can be renewed exactly once; a second renewal attempt returns HTTP 409.
- [ ] The `DELETE /api/v1/bookings/lock/{lock_token}` endpoint successfully releases the lock; subsequent initiation attempts for the same listing and dates succeed.

### AC-6.2 — Booking Reference
- [ ] Every `bookings` row has a `reference` matching the pattern `KAIN-\d{4,}-[A-Z]{2}`.
- [ ] No two bookings share the same reference (UNIQUE constraint enforced).
- [ ] The country code in the reference matches the listing's country code.

### AC-6.3 — Pricing Integrity
- [ ] The server-side computed `total_amount` stored on the booking matches the formula in BR-6.11 / BR-6.12 for all test cases (standard stay, long-stay discount applied, car with delivery).
- [ ] A change to `listings.nightly_rate` after a booking is `confirmed` does not alter `bookings.total_amount`.
- [ ] `commission_amount + provider_payout = total_amount` (within rounding tolerance of ±0.01).

### AC-6.4 — Status Transitions
- [ ] A booking cannot be transitioned directly from `pending_payment` to `completed`.
- [ ] A booking cannot be cancelled once it is in `completed` status (HTTP 409 returned).
- [ ] Every status change produces a row in `booking_status_log` with the correct `from_status` and `to_status`.

### AC-6.5 — Cancellation Refunds
- [ ] A guest cancelling a `free` policy booking 72 hours before check-in receives `refund_amount = total_amount` (100%).
- [ ] A guest cancelling a `strict` policy booking 10 days before check-in receives `refund_amount = total_amount × 0.5` (50%).
- [ ] A provider-initiated cancellation always sets `refund_amount = total_amount` regardless of the listing's cancellation policy.

### AC-6.6 — Automated Completion
- [ ] The nightly Scheduler job transitions all `confirmed` bookings with `check_out < CURRENT_DATE` to `completed`.
- [ ] The `booking.completed` event is published for each transitioned booking, enabling the review prompt (E14).

### AC-6.7 — Licence Plate Privacy
- [ ] `GET /api/v1/guests/me/bookings/{id}` for a car booking returns the decrypted licence plate string only when `booking.status IN ('confirmed', 'completed')` and the requesting user is the booking guest.
- [ ] The same endpoint returns no `licence_plate` field when the booking is `cancelled_by_guest`, `cancelled_by_provider`, or `cancelled_by_system`.
